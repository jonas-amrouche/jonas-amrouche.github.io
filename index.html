FireLive

The idea for this project was to make a software for live mixing and live producing with integrated loop buffers, entirely customizable and usable with any custom controllers.

It's not complete as it lacks lots of features I have in mind, but the basics are there.

I made the first working version in 1 week and used it in a little 30 minute set with a friend, it was quite fun. I made it with Godot Engine to iterate fast on the UI side, and to use the Godot Audio Engine.

After the first week I refactored all my code, fixed some bugs, polished some features, and started working on a C++ gdextension for all the computing intensive tasks, like generating the audio spectrum or adding additional audio effects.

Before Firelive I had already developed a little application game called Firestage.


It's a VJing app, not as advanced, where you can mess with lights, smoke, fire and laser in front of a crowd, it's not really advanced, as it was supposed to be customizable, but it's fun to play.

I love live shows, lighting and audio techniques that hype up a crowd, and I hope I can one day work on something like that.

Server Meshing

I have recently tried to create a scalable multiplayer-game networking architecture based on the idea of "not much replication, lots of users" (don't search on the internet I made that up). I thought that if I could achieve a cool multiplayer MMO concept without complex replication or persistence,
I could have a never before seen number of players connected to a single world.

Quite a naïve idea, but projects must start somewhere.
I started with a simple game server and a proxy server to tell players which game server to connect to. Then I modified game servers to mesh into each other, the proxy server also helped the game servers to connect to each other. It was time to make some improvements, I added, basic security for client - server communication (pickling/serializing packets), player load balancing and game server redundancy. Everything worked great so I decided to add VOIP, at first I used an all purpose compression algorithm for the packet transmission which was terrible. To do this more efficiently I learned that I had to use Opus, the industry open standard for voice/sound transmission, but Opus is not natively supported by Godot. So I forked a C++ Godot gdextension github repo that was almost doing what I needed, and modified/optimized it to get what I wanted in a practical workflow. I was done with the architecture so I got an OVH server, and after tackling numerous bugs it worked !

I'm very proud of this project not because it led anywhere but because it was a real challenge that taught me a lot.

Elumin

Elumin is the biggest project I have worked on.

It's an atmospheric game in a fictional place, I worked on it alone in my free time for the past 4 years, writing and re-writing the story, making and re-making models, programming and re-programming features.
Over the years, and more recently I had to develop my own tools to fix performance issues, mainly 3D issues : draw calls count, lights and shadows, video memory. All of this led to terrible performance.
Some of the issues were deeply related to my workflow, which I wanted to preserve because of the ease of use and fast iterating capabilities.
To keep this workflow, I had to develop a blender add-on in python using the Blender API.
This add-on allowed me to assign a countless amount of different materials to any parts of a model without having to bake textures.

It was a fascinating problem-solving game to extract every bit of performance I could. At the time, the project is not remotely near what I have in mind for it to be good, but it's the only project where I allow myself to not think about a deadline.

Elumin has a STEAM PAGE, maybe it will be complete one day.

Metronim

For this project I was inspired by all ".io" party game sites, it was back in 2021 and I wanted to be the next skribl.io, I guess.

I was not very experienced in web development but it didn't appear too hard because I was already developing games and applications for years.
It was a slow learning process and not my best work, especially on the graphical side, because I was doing everything in vanillaJS using a good old canvas.

At first it was not about trains and explosions, but about hacking (more in the vein of s0urce.io), but with a couple of friends.

There was a secret password that you wanted to guess from a player, another secret password that you wanted a player to guess, all of that with a "private" chat functionality, and you had tools to see or hijack communications.

I remember that it was too hard to make the game fun and interesting, that's why I embraced ✨the train approach✨.
